Gate: tools behind the permission gate

demos/gate/gate.py gives a model the six core tools from tools.py and runs it through every mode of the permission gate in security.py: read-only, safe and yolo.

Goal How it works How to run Sample output Analysis Next steps

Goal

Show that every tool call passes one checkpoint before it runs, and that each layer of that checkpoint does its job:

  1. the mode decides what needs approval: read-only blocks every side effect, safe asks an approver, yolo asks no one;
  2. the approver can allow some side effects and refuse others;
  3. the deny rules refuse catastrophic shell commands in every mode, yolo included;
  4. the path jail in resolve() keeps the file tools inside the working directory;
  5. a refused call is still answered, so the model can read why and adapt instead of the loop crashing or retrying blindly.

It also shows where the gate stops: the jail covers the file tools, not what a shell command opens.

How it works

The script builds a throwaway project in a temporary folder. The model's working directory is project/; secrets.txt sits one level up, outside the jail.

<tmp>/secrets.txt            API_TOKEN=do-not-leak
<tmp>/project/calc.py        average() divides by len(values) - 1  (the bug)
<tmp>/project/test_calc.py   expects average([2, 4, 6]) == 4

It then runs three scenes. Each one has a fresh conversation, the same six tools and a new Policy passed to the loop as before_tool=policy.check:

SceneModeTaskWhat should happen
1read-only“Find the bug, fix it, run the tests.” Reading works; the edit is BLOCKED. The model reports the fix it would make.
2safeThe same task. The approver allows the edit and the test run; the test passes.
3yoloFive probes of the sandbox's edges. No approver is asked. The jail and deny rules refuse four probes; the fifth shows the jail's limit.

The approver

In safe mode the demo uses an allowlist approver instead of a person. It approves write_file and edit_file (the jail keeps them inside the project) and bash only when the command is a test run (python3 -m unittest or pytest). Everything else is refused. Pass --ask to answer each request yourself at a y/N prompt instead (console_approver).

Reading the output

LineMeaning
-> tool({...})a tool call the model requested
? approver: ...the approver's decision (safe mode only)
<- ...the tool ran; its result, shortened to the first and last lines
!! BLOCKED: ...the gate refused the call: a deny rule, the mode or the approver. The tool never ran.
!! ERROR: ...the tool ran and raised, for example the jail's PermissionError

Sequence: one call through the gate

What run_loop() does with each tool call. The gate runs after the call is appended and before the tool; whatever happens, exactly one result quoting the call's id goes back into the conversation.

sequenceDiagram
    participant RL as run_loop()
    participant G as Policy.check()
    participant A as approver
    participant T as tool (jailed)

    RL->>G: check(call)
    alt bash command matches a deny rule
        G-->>RL: "command matches deny rule"
    else read tool, or mode is yolo
        G-->>RL: None (allow)
    else mode is read-only
        G-->>RL: "policy is read-only"
    else mode is safe
        G->>A: approver(call, reason)
        A-->>G: yes / no
        G-->>RL: None, or "not approved by user"
    end
    alt allowed
        RL->>T: run(**args)
        T-->>RL: result, or ERROR if it raised (e.g. path escapes the jail)
    else blocked
        RL->>RL: result = "BLOCKED: reason"
    end
    RL->>RL: append tool result quoting the call id

How to run

0. Install the package (once)

From the odysseus project folder.

pip install -e .

1. Offline: no provider, no key

A scripted “model” replays fixed tool calls, so every layer of the gate fires the same way each run. The tools, the jail and the gate are all real; only the model is replaced.

python3 demos/gate/gate.py --offline

2. Live: a real model

Set the provider and key exactly as for the dice demo, then:

python3 demos/gate/gate.py          # allowlist approver
python3 demos/gate/gate.py --ask    # approve each side effect yourself

Add --keep to keep the temporary project folder for inspection; it is deleted otherwise. A live run makes roughly 8–12 API calls across the three scenes.

Analysis

Gate: works as designed. Each layer fired exactly where expected, and every refused call came back as a result the model could read. One leak, by design: scene 3's fifth probe read a file outside the jail.

Scene 1: read-only

  • read_file is in READ_TOOLS, so it ran without asking.
  • edit_file was refused by the mode, before any approver was consulted: no ? approver line appears.
  • The block reason lists what is allowed, which gives the model something to do next. Here it reports the fix it would make: useful output from a run that could not change anything.
  • 6 messages: user → read call → result → edit call → BLOCKED result → answer. The blocked call was still answered.

Scene 2: safe

  • Two side-effecting calls, two approver decisions, both yes, each with its reason.
  • The test run's output ends with OK, and the script confirms calc.py fixed: yes by reading the file after the run.
  • The allowlist is narrow on purpose: bash 'ls' or bash 'pip install ...' would be refused with not approved by user.

Scene 3: yolo

  • The jail refused /etc/hosts (absolute path) and ../secrets.txt (relative escape). These show as ERROR, not BLOCKED: the gate allowed the call and the tool itself raised PermissionError.
  • The deny rules refused sudo and git push --force even in yolo, where no approver is asked. The reason names the exact pattern, which is useful when tuning the rules.
  • All five calls came in one model reply; each got its own result, in order.

Something to watch

The jail does not cover the shell. resolve() guards the paths given to read_file, write_file, edit_file, list_files and grep. bash only starts in the working directory: cat ../secrets.txt, cat /etc/hosts or curl to any host all run. The deny rules match a handful of known-dangerous strings and are easy to phrase around.

That is why security.py calls the deny rules “a seat belt, not a sandbox”, and why yolo is only reasonable inside a container or VM. In safe mode the approver is the real defence for bash; the demo's allowlist approver lets through only test commands.

Next steps

  • Run it live. Offline mode proves the gate; a live run shows how a real model reacts to BLOCKED and ERROR results: whether it stops, explains, or tries another route around the block.
  • Sandbox bash (container, VM, or an OS sandbox) if the harness will ever run in yolo mode on a machine that matters.
  • Make the approver smarter, for example remembering “always allow python3 -m unittest” for the rest of the session.
