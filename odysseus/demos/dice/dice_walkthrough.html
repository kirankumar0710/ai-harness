Dice: the agent loop with one tool

demos/dice/dice.py is the smallest end-to-end run of the odysseus_v2 harness: a real model, one harmless tool, two tasks.

Goal How it works How to run Sample output Analysis Next steps

Goal

Confirm against a real vendor API that the harness:

  1. sends a request the vendor accepts (system prompt, tools, history in its wire format);
  2. parses the model's tool call, runs the tool and returns the result quoting the call's id;
  3. lets the model decide when it is finished, so the loop ends on its own;
  4. behaves sensibly when the available tool cannot help: the model answers in text instead of misusing the tool (judgment without hands).

The unit tests check the same formats offline with a fake transport; this demo is the only thing that proves a real API accepts them.

How it works

The script defines one tool, roll_dice(count), which returns count random values from 1 to 6 (1–20 dice allowed; anything else raises an error that the model sees as a tool result). It then runs two tasks, each with a fresh conversation and max_turns=10:

TaskCan the tool help?Expected messages
“Roll 3 dice and tell me whether the total beats 10.”Yes user → assistant (tool call) → tool result → assistant answer = 4
“Build a landing page for a coffee shop.”No user → assistant answer = 2

Each turn of the loop is: call the model → append its reply → if it asked for no tools, stop → otherwise run every tool call and append each result. An event handler prints each step, prefixed as follows:

LineMeaning
user:the task sent to the model
assistant:text the model wrote (omitted when it only called a tool)
[tokens in N, out M]usage for that model call
-> roll_dice({...})a tool call the model requested, with its arguments
<- [...]the tool's result, sent back to the model
(N messages in the array)size of the conversation when the task ended

How the dice task travels through the harness (see the architecture in the README for the parts). It takes two turns: in the first the model asks for the tool, in the second it answers. The message count after each step is shown in brackets.

    D->>RL: run_loop(provider, system, messages, tools)
    Note right of D: messages = [user: Roll 3 dice...]  [1]

    RL->>P: complete(system, messages, roll_dice schema)
    P->>API: POST /v1/messages
    API-->>P: tool_use roll_dice, count 3
    P-->>RL: Completion with 1 tool call

    RL->>RL: append tool result, quoting the call id  [3]

    Note over RL,T: Turn 2: the model answers
    RL->>P: complete(system, messages, roll_dice schema)
    P->>API: POST /v1/messages, history includes tool_use and tool_result

    P-->>RL: Completion with no tool calls
    RL->>RL: append assistant message  [4]
    RL-->>D: final answer text

Task 2 (the landing page) is a single turn: the model replies with text and no tool call, so run_loop() returns after the first complete() with 2 messages.

How to run

0. Install the package (once)

From the odysseus project folder (cd ai-harness/odysseus). -e (editable) links the install to your checkout, so code changes take effect without reinstalling.

pip install -e .

1. Choose a provider

Required; there is no default.

export ODYSSEUS_PROVIDER=anthropic   # or gemini / openai / openrouter

2. Export that provider's API key

The variable name is the api_key_env entry for the provider in src/odysseus_v2/providers/providers.ini. ODYSSEUS_API_KEY works for any provider as a fallback.

ProviderKey variable
anthropicANTHROPIC_API_KEY
geminiGEMINI_API_KEY or GOOGLE_API_KEY
openaiOPENAI_API_KEY
openrouterOPENROUTER_API_KEY
export ANTHROPIC_API_KEY=...

3. Run, from the odysseus folder

python3 demos/dice/dice.py

The base URL and model come from providers.ini. To use different ones, point ODYSSEUS_CONFIG at your own .ini file, or set ODYSSEUS_MODEL. openai has no default model, so you must set one for it. If the provider or key is missing, the script prints which variable to set and exits with code 1. Each run makes three or four real API calls.

Analysis

Result: pass. Config and ini loading, the Anthropic request format, tool calling, response parsing and the loop all worked against the live API.

Task 1: dice (the tool can help)

  • 4 messages, as expected: user → tool call → tool result → answer.
  • The model chose the tool on its own and passed the correct argument (count: 3).
  • The result [6, 5, 5] was sent back with the call's id and the API accepted it, so the conversion of tool calls and results to Anthropic's format is correct.
  • The answer is correct: 6 + 5 + 5 = 16, which beats 10.
  • Token usage was parsed for both calls. The second call's input grew from 421 to 484 tokens because it carries the tool call and result.

Task 2: landing page (the tool cannot help)

  • 2 messages, as expected: the model did not call roll_dice, so the loop ended after one turn.
  • The model has no tool to write files, so it put the whole page in its text reply. That is the intended judgment without hands: it knows what to build but cannot act on it.
  • It also knew what it could not do: it says the contact form "doesn't send anywhere yet" and suggests services to connect it to, instead of claiming a working form.
  • The reply is not deterministic. Two runs produced different pages (one with a newsletter form, one with "Why Us" cards and a contact form) and different lengths: 4,533 and 5,454 output tokens.
  • The closing offer ("I can also adapt it to React or Tailwind") cannot be taken up here. The demo ends the conversation after each task, so there is no turn in which a user could reply. The model offers because that is what it does in a chat; a harness that wants follow-ups has to keep the messages list and call run_loop again with the next user message.

Something to watch

Silent truncation risk. The landing-page reply used 5,454 output tokens, two-thirds of the default limit (max_output_tokens = 8192 for Anthropic), up from 4,533 in an earlier run. Length varies from run to run, so a longer reply would eventually be cut off at the limit, and the harness would not notice: the providers ignore the vendor's stop reason (stop_reason: "max_tokens" for Anthropic, finishReason for Gemini, finish_reason: "length" for OpenAI).

The 5,454 tokens are the size of the whole model reply: the introduction, the HTML, and the "What's included" and "Customizing" notes after it. All of it counts towards the limit. A reply that hits the limit loses its end, which here means these notes or even the closing </html> tag, leaving a page that looks complete in the transcript but is broken.

The loop would then treat the cut-off text as a finished answer. Fix: check the stop reason in each provider and raise an error or emit a warning event when output was truncated.

Next steps

  • Run with Gemini. This run only covered the Anthropic adapter. Gemini has the most vendor-specific handling (reasoning signatures that must be sent back, locally generated call ids, empty message parts), so it is the most worth checking.
  • Run with OpenAI or OpenRouter to cover the third request format.
  • Handle the stop reason so truncated replies are reported instead of passed off as complete.
