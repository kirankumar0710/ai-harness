Durability: crash, resume, and a sub-agent

demos/durability/durability.py kills an agent's process in the middle of a tool call, then resumes the task in a new process from the session log alone. It then answers one question twice, once reading the files itself and once through a sub-agent, and compares how big the parent's conversation gets.

Goal How it works How to run Sample output Analysis Next steps

Goal

An agent's whole memory is its conversation, held in one process. Two things follow:

  1. Durability. If the process dies, the conversation dies with it, unless every message was written down as it happened. session.py appends each message to a JSONL file in .odysseus/sessions/, and open_session(..., resume=True) replays it. The hard case is a death during a tool call: the call is in the log, its result is not, and its side effect may already have happened.
  2. Sub-agents. Everything an agent reads stays in its conversation and is sent again on every request. spawn_agent (subagent.py) hands a self-contained task to a fresh agent, whose reading stays in its conversation; the parent receives only the report.

How it works

Part 1: a task with a side effect

The project is an empty folder. The agent gets read_file, list_files and one demo tool, apply_step, which appends a line to applied.log. The task:

Apply setup steps 1 to 3 in order with the apply_step tool. Each step must be applied
exactly once: applying one twice breaks the setup. applied.log records every step applied
so far.

The tool, as the first process sees it. After writing step 2 the process kills itself with SIGKILL: no exception, no finally, no cleanup, exactly like kill -9 or a power cut:

def apply_step(number: int) -> str:
    with open("applied.log", "a") as f:
        f.write(f"step {number} applied\n")
    if crash and number == 2:
        os.kill(os.getpid(), signal.SIGKILL)     # the side effect happened; the result never will
    return f"Applied step {number}."

So the first process is a real, separate Python process (the demo starts it with subprocess), and the resume happens in the demo's own process, which knows nothing about the first one except the files it left behind.

sequenceDiagram
    participant P1 as first process
    participant L as session log (.jsonl)
    participant F as applied.log
    participant P2 as new process

    P1->>L: user: the task
    P1->>L: assistant: apply_step(1)
    P1->>F: step 1 applied
    P1->>L: tool: Applied step 1.
    P1->>L: assistant: apply_step(2)
    P1->>F: step 2 applied
    Note over P1: SIGKILL: the result of step 2 is never logged
    P2->>L: open_session(resume=True)
    L-->>P2: 4 messages, the last call has no result
    P2->>L: repair: apply_step(2) answered with "interrupted, may or may not have run"
    P2->>L: user: Continue the task.
    Note over P2: the model must check applied.log before repeating step 2
    P2->>F: read applied.log, then apply step 3 only

Why the repair matters: every vendor rejects a conversation with a call that has no result, so the log as written could not be continued. repair() answers the call, and the answer is honest. It says the call may or may not have run, which is true here: step 2 did run. A repair that said “did not run” would invite the model to apply step 2 a second time. The check at the end counts the lines in applied.log: every step exactly once, or not.

Part 2: a question that needs a lot of reading

A fresh project holds six note files, notes/auth.md to notes/search.md. Each has a heading, 40 filler lines and one last line. Two of them end with a deadline:

# notes/billing.md (42 lines)
# billing notes
Meeting note 001: billing discussed, no decision needed.
... 38 more filler lines ...
Meeting note 040: billing discussed, no decision needed.
DEADLINE: 2026-12-01 - switch invoices to the new tax rates

The others end with No deadline set for this area. (notes/search.md has DEADLINE: 2027-01-15.) The tools are read_file and list_files, with no grep, so the files have to be read. The question is asked twice, in a fresh project each time:

RunTaskWhere the six files end up
2a“Which areas in notes/ have a deadline, and when is each due? Answer with one line per area.”in the parent's conversation, sent again on every later request
2bThe same, plus “Delegate the reading to one sub-agent with spawn_agent and answer from its report; do not read the notes yourself.” in the sub-agent's conversation; the parent gets only the report

Run 2b passes subagent_depth=1 to run_task(), which adds the spawn_agent tool. The child runs under the same mode (read-only here) with the same two tools. It cannot spawn again (depth 0) and keeps no session log.

        M-->>C: list_files, read_file x6

    C-->>P: the report, as the result of spawn_agent
    P->>M: question + one call + two-line report
    M-->>P: final answer

How it is measured

One provider serves both parent and child, wrapped in a Meter. A request belongs to the sub-agent when its system prompt contains SUBAGENT_PROMPT. Sizes are estimated at four characters per token, and also recorded as the vendor reports them (offline: nothing is reported, shown as -).

How to run

From the odysseus project folder.

pip install -e .

1. Offline (no API key)

python3 demos/durability/durability.py --offline

2. Against a real model

Set the provider and key as in the dice demo, then:

python3 demos/durability/durability.py

To save the complete output to output/, use python3 demos/record.py durability [--offline]. Part 1 needs a system with SIGKILL (macOS or Linux).

Analysis

Part 1: the crash and the resume

Every step was applied exactly once. The first process was killed by signal 9 after logging 4 messages. The last of them is the call apply_step(2), with no result, while applied.log already held steps 1 and 2. On resume, repair() answered 1 call as interrupted. The model read applied.log, found step 2 there, and applied only step 3. The log ends with 11 messages, including the repair, so a second resume would replay the same valid history.

The outcome depends on the model reading the error and checking before it acts. The scripted model is written to do that, so the offline run shows what the harness provides (a valid history and an honest error), not what a real model will do with it. A live run is the real test.

Part 2: before and after a sub-agent

2a: reads itself2b: with a sub-agent
largest parent request (est.)4,411596
parent messages at the end114
tokens sent by the parent (est.)5,2021,081
tokens sent by the sub-agent (est.)05,373
tokens sent in all (est.)5,2026,454

The parent's context stayed small. Its largest request was 4,411 estimated tokens when it read the six files itself, and 596 when a sub-agent read them: 7.4 times smaller. Its conversation ended with 4 messages instead of 11. Both runs found both deadlines.

It is not cheaper. In all, run 2b sent 1,252 more estimated tokens (24% more): the child pays for its own system prompt and tools, and the parent for one more round trip. The files were read once either way. A sub-agent saves the parent's context, which matters when the parent has much more work to do after the reading. Each later parent request would carry 3,815 fewer tokens. It does not save tokens on a task this short.

The repair can only be honest, not certain. The log cannot tell whether an interrupted call ran. A step that is safe to repeat needs no care. One that is not (a payment, a migration, an email) needs a check the model can make, like applied.log here, or a tool that refuses to apply a step twice.

The session log holds everything the model saw, including file contents and command output, so it can hold secrets. It is in .odysseus/, which is git-ignored and refused by the file tools, but bash can still read it.

Next steps

  • Record a live run and compare: does a real model check applied.log before repeating step 2, and does it delegate when told to?
  • Make tools idempotent where it matters: an apply_step that refuses a step already in applied.log would make part 1 safe whatever the model does.
  • Let the model choose to delegate: drop the instruction from task 2b and see whether it uses spawn_agent on its own.
