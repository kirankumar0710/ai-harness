Memory: the same task, before and after

demos/memory/memory.py runs one task twice in fresh conversations: first with no memory, then with the note the agent saved the first time. A table at the end shows what the note saved.

Goal How it works How to run Sample output Analysis Next steps

Goal

A conversation ends and its messages are gone. Memory is what survives: short facts in AGENT_MEMORY.md, a file in the project that memory.py loads into the system prompt of every new session. The demo shows, with numbers, what that buys:

  1. the agent saves a fact it had to discover, with the remember tool;
  2. a new conversation, sharing no messages with the first, starts with that fact already in its system prompt;
  3. so the same task takes fewer calls, fewer tokens and no wasted steps the second time.

How it works

The project and its hidden facts

The throwaway project has the familiar average() bug, but its checks are not where a model expects tests to be, and they refuse to run without a setting:

# calc.py
def average(values):
    """Return the arithmetic mean of a non-empty list of numbers."""
    return sum(values) / (len(values) - 1)

# checks/check_calc.py
import unittest

from calc import average


class AverageCheck(unittest.TestCase):
    def test_average(self):
        self.assertEqual(average([2, 4, 6]), 4)

# checks/__init__.py
import os

if os.environ.get("CALC_CHECKS") != "1":
    raise ImportError("these checks only run with CALC_CHECKS=1 set")

So every obvious command fails, and only the error says why:

$ python3 -m unittest
ImportError: these checks only run with CALC_CHECKS=1 set
FAILED (errors=1)

$ python3 -m unittest discover -s checks -p 'check_*.py' -t .
ImportError: these checks only run with CALC_CHECKS=1 set
FAILED (errors=1)

$ CALC_CHECKS=1 python3 -m unittest discover -s checks -p 'check_*.py' -t .
Ran 1 test in 0.000s
OK

The file names (check_*.py) can be seen in a listing, but the setting can only be learned by running the checks and reading the error, or by opening checks/__init__.py, which models rarely do. That makes it a fact worth remembering: the run that discovers it pays for a failed run; the next one should not.

An earlier version hid only the file names. A live model worked those out by reading one file, so memory had little to save (see the live run below).

The two runs

Both runs send the same task, through run_task() in safe mode:

The checks for this project fail. Fix the bug in calc.py and confirm the checks pass. Before you finish, use the remember tool to save anything a future session would need to know about working in this project, unless it is already in project memory.
RunBefore it startsWhat it shows
1. without memoryNo AGENT_MEMORY.md. The system prompt has no memory section. The cost of discovering the command, and the note saved at the end.
2. with memorycalc.py is reset to the buggy version, but AGENT_MEMORY.md from run 1 is kept. A fresh conversation: no messages from run 1. The same task, starting from the note.

How the note gets into the next session

The remember tool (from memory_tools()) appends one line to AGENT_MEMORY.md. At the start of every task, run_task() calls build_system_prompt(), which adds the file's contents as a section. In run 2 the model's system prompt contains:

Project memory (AGENT_MEMORY.md):
- Checks live in checks/check_*.py, so plain 'python3 -m unittest' finds none; run them with: python3 -m unittest discover -s checks -p 'check_*.py' -t .

When there is no memory yet, the section says so: Project memory (AGENT_MEMORY.md): none yet. Nothing has been saved for this project. Without that line, a model that knows about the file goes looking for it.

remember writes a file, so the gate treats it as a side effect: blocked in read-only mode, asked about in safe mode. The demo's approver allows file edits, remember, and python -m unittest commands. A test command may start with settings such as CALC_CHECKS=1, and end with 2>&1 or | tail, which only change how output is shown; any other shell operator (;, &&, a pipe into another program) means a second command, and is refused. A refusal says what would be approved, so the model can try again in that form.

The task ends “unless it is already in project memory”, so the second run does not save the same fact again, or notes about itself.

How to run

From the odysseus folder, after pip install -e .:

python3 demos/memory/memory.py --offline   # scripted model, no key needed
python3 demos/memory/memory.py             # a real model; provider and key as in the dice demo

Add --keep to keep the temporary project and read its AGENT_MEMORY.md.

Analysis

Before and after

  • The difference is the discovery. Run 1 listed the files, ran plain unittest (0 tests, wasted), then worked out the real command. Run 2 ran the real command first time, because its system prompt already said what it was.
  • The note crossed a conversation boundary. Run 2 shared no messages with run 1. The only link is the file, which is the point of memory.
  • Offline proves the plumbing, not the model. The scripted model follows a script either way. What is real: remember wrote the file, and the file reached run 2's system prompt.

Live run: run 1 had to fail; run 2 did not

without memorywith memory
model calls75
tool calls95
wasted calls21
tokens sent (reported)16,53711,275
checks passyesyes

32% fewer tokens, about half the tool calls. Memory saved what it is meant to save: the discovery.

  • Run 1 paid for the discovery. It found the check files from the listing and guessed the discover command, but the run failed: ImportError: these checks only run with CALC_CHECKS=1 set. It then chained cat checks/__init__.py; CALC_CHECKS=1 ..., which was refused with a reason, so it read the file and ran the command separately, and saved the note.
  • The note is about the project only: “Run checks with: CALC_CHECKS=1 python3 -m unittest discover ... (CALC_CHECKS=1 is required or import fails).” The previous run's note also recorded the approver's rules (“bash tool only approves 'python3 -m unittest ...' commands ...”), facts about this harness that would go stale if the approver changed. The clearer remember description, “not about your own tools, permissions or this session”, kept them out.
  • Run 2 started from the note: no listing, no failed import. Its one wasted call was a chain, cat calc.py; ls; ls checks; CALC_CHECKS=1 ..., refused with a reason; it then ran the parts separately.
  • No duplicate note. Run 2: “project memory already has it, including the CALC_CHECKS=1 requirement.”

A trade-off this shows. In the previous run, the note about the approver's rules saved run 2 from that chained command: it had no wasted calls and saved 46%. Keeping such notes out cost one refused call here. It is still the right trade: a wrong note misleads every later session, while a refused call costs one turn and says what to do instead.

fix verified by the agentyesno

Memory itself worked. Run 2's first call was the correct check command, straight from AGENT_MEMORY.md: no listing, no reading the check file, no guessing. That is the saving the demo was built to show. The numbers hide it for three reasons, all in the demo's design, not in memory.py:

  1. The approver blocked the remembered command. Run 2 ran it with 2>&1 appended, to see errors too. The demo's approver refuses any shell operator, so both attempts were blocked, and the agent finished without running the checks. Every extra call and token in run 2 comes from working around that.
  2. The hidden fact was not hidden enough. Run 1 read checks/check_calc.py, worked out the discover command and got it right first time. It never ran plain unittest, so there was little discovery for memory to save.
  3. Run 2 saved a bad note. The task asks every run to save what a future session needs, so run 2 added: “In one session, the bash tool was blocked (‘not approved by user’), so the checks could not be run.” That is a fact about one session's approver, not about the project, and it would now be in every future system prompt. This is the risk under “Something to watch” below, happening for real.

Fixed since: the approver now accepts a test command ending in 2>&1 or | tail -N, and the task asks for notes only when they are not already in memory. Reason 2 (the fact was easy to work out) is unchanged: memory still saves the listing, reading and guessing, as run 2 showed. The live run above shows the corrected table.

Token counts: the estimate (2,842) is far below what the vendor reported (10,345) because it counts only the messages and the system prompt. Every request also carries the eight tool schemas, over 1,000 tokens each time. See the context walkthrough, where the same gap matters more.

Something to watch

A wrong note is worse than no note. Memory is loaded into every session and trusted. If the agent saves something mistaken, or the project changes and the note goes stale, every later session starts from the wrong fact. AGENT_MEMORY.md is a plain file: read it, fix it, and commit it like code.

Memory costs context on every call. Unlike a skill, it is never loaded on demand. memory.py caps it at 20,000 characters and keeps the newest notes, but a long memory still makes every request bigger. Keep notes short and few.

Next steps

  • Approve chains of allowed commands (an idea, not planned): models often bundle commands with ;. An approver could split a chain and approve it when every part is allowed, but parsing shell safely is hard to get right.
  • Plant a stale note (the old, wrong command) before run 2, to see whether the model trusts memory over what it observes.
  • Run 1 in read-only mode to show remember blocked by the gate, and run 2 starting with nothing.
