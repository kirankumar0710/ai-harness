Context: the same long task, before and after compaction

demos/context/context.py runs one long task twice: with no limit on the conversation's size, then with a small budget that forces compaction. A chart and a table at the end show what compaction saved, and whether the answer survived it.

Goal How it works How to run Sample output Analysis Next steps

Goal

Every request sends the whole conversation so far. On a long task each request is bigger than the last, until it no longer fits the model's context window, and the total cost grows much faster than the work. Compaction (Compactor in context.py) folds the oldest turns into a summary the model writes, once the conversation passes a budget. The demo shows:

  1. without compaction, request size keeps growing;
  2. with compaction, it levels off near the budget, and fewer tokens are sent in total;
  3. the agent still gets the right answer, even though the turns that found most of it were replaced by a summary.

How it works

A task that has to be long

The project's data/ folder holds a chain of 8 files. Each has 40 lines of filler, one VALUE, and the name of the NEXT file:

# data/start.txt   (2,165 characters)
Chain file 1.
Log line 001: routine entry, nothing to act on here.
Log line 002: routine entry, nothing to act on here.
... (35 more filler lines) ...
Log line 039: routine entry, nothing to act on here.
Log line 040: routine entry, nothing to act on here.
VALUE: 17
NEXT: data/amber.txt

Because each file names the next, and the agent gets only read_file and write_file, it must read them one at a time: eight turns, each adding about 650 tokens to the conversation. (With grep the model could pull every VALUE and NEXT line in one call, and the conversation would never grow, so the task is limited to these two tools with run_task(..., tools=...).) Four decoy files sit in the same folder with values 100–400 that must not be counted. An agent that loses track of which files were in the chain gets an obviously wrong total. The right total is 156.

The task, the same in both runs:

Start at data/start.txt. Each file in the chain has a VALUE and names the NEXT file to read. Follow the chain to the end, add up the VALUEs of the files in the chain only, and write the total to TOTAL.txt as a single number.

The two runs

RunBudgetWhat happens
1. without compactionunlimited Every file read stays in the conversation.
2. with compaction5,000 tokens Before each request, the compactor checks the size: the messages plus the system prompt and tool schemas, which go out with every request. Over budget, it keeps up to the newest 6 messages, fewer if needed so that what is kept fits in half the budget, and replaces everything older with a summary.

Three rules keep the history valid for every vendor: the cut never separates a tool call from its result, the conversation still starts with a user message, and two user messages never sit side by side. The summary is asked to preserve the task, files touched, decisions, errors and what remains:

You compress agent transcripts. Preserve: the original task, every file created or edited and its purpose, key decisions, unresolved errors, and what remains to be done. Be dense and factual.

How it is measured

The demo wraps the provider in a Meter that records the size of every request, the agent's and the compactor's summary requests, at four characters per token, counting the system prompt and tool schemas the same way the compactor does. After each run it reads TOTAL.txt.

How to run

From the odysseus folder, after pip install -e .:

python3 demos/context/context.py --offline   # scripted model, no key needed
python3 demos/context/context.py             # a real model; provider and key as in the dice demo

Offline, the scripted model is honest about what it can see: the total it writes comes only from the values still in its conversation (kept messages and summary), and its summaries list only values visible in the transcript it was sent.

Without compaction each request carries everything before it, so it grows by about 970 tokens per file read, to 8,867. With compaction the line is the same for five requests. The sixth would have passed 5,000, so the compactor folded nine messages first and the request went out at 2,308. Three reads later it folded again, to 2,373. Every request stayed under the budget.

  • Two folds, each reaching its target. After each fold the request was about 2,100–2,200 (estimated) against a target of half the budget, 2,500, so there was room to work between folds and no budget_warning.
  • 31% fewer tokens in total (51,746 against 35,664 reported), including the two summary calls. The largest request was 4,764 instead of 8,867. On a longer task the gap keeps widening: without compaction the size grows with every step; with it, it stays within the budget however long the task runs.
  • The summary kept every value and a running total, “125 (through fjord.txt; not final)”, and the model's interim answer, “Sum: 125 + 31 = 156”, adds the last value to it. The answer is correct, with 7 messages left instead of 21.
  • The estimate is still low. The demo's own estimate of the largest request was 3,045 against 4,764 reported. The compactor no longer relies on it: after the first request it measures from the reported sizes.

Something to watch

Compaction is lossy, and the model decides what is lost. The summary prompt asks for the task, files, decisions and errors. It does not mention intermediate results like the values here. A live model may keep them, or may write “read five files” and lose the numbers. If a task depends on details found along the way, the summary prompt has to say so, or the agent should write them to a file as it goes.

The first request is an estimate. Once the vendor has reported a size, the compactor measures from it. Until then, and offline, it uses four characters per token, which is rough: code, digits and non-English text use more tokens per character. Set the budget well below the model's real context window.
