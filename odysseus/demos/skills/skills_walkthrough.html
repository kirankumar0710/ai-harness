Skills: instructions loaded only when needed

demos/skills/skills.py gives a model two skills, a release-note guide and a migration-review checklist, and three tasks. It shows which skill the model loads for each task, and whether it followed the instructions.

Goal How it works How to run Sample output Analysis Next steps

Goal

A skill is a packet of instructions for one kind of task, such as “how to write a release note” or “how to review a database migration”. It is stored as a file the agent can read, not as code. The demo shows the three things that make that useful:

  1. Reusable instructions for a type of task. Each skill sets a format specific enough that the model could not guess it. If the output matches, the model followed the skill.
  2. Stored separately, as files. Both skills are plain SKILL.md files checked in next to the script. Adding a skill means adding a folder; no harness code changes.
  3. Loaded only when relevant. Every prompt carries only each skill's one-line description. The full text enters the conversation only when the model calls use_skill, and one of the three tasks needs no skill at all.

How it works

The two skills

A skill is a folder with one SKILL.md. The folder name is the skill's name. The description in the front matter (between the --- lines) is the only part the model sees up front; everything below it is the instructions. These files are in demos/skills/example_skills/.

# example_skills/release-note/SKILL.md
---
description: How to write a release note for a change in this project
---
# Writing a release note

Add the new entry to RELEASE_NOTES.md, directly under the
"# Release notes" heading, in exactly this format:

    ## <version> - <YYYY-MM-DD>
    ### Fixed
    - <what was wrong, in words a user understands> (<file changed>)
    Upgrade: <what a user must do, or "no action needed">

Rules:
- Use the version and date given in the task. Never invent them.
- One line per change, past tense, no code or jargon.
- Put the changed file name in brackets at the end of the line.
- Always include the Upgrade line, even when nothing is needed.
- Never edit or reorder older entries.
# example_skills/review-migration/SKILL.md
---
description: How to review a database migration before it is merged
---
# Reviewing a database migration

Read the migration file, then check these four points, in this order.
Report each on its own line as PASS or FAIL, with one short reason:

1. Reversible: is there a matching down migration (the same name with
   .down.sql) that undoes it?
2. Locking: does it add a NOT NULL column without a DEFAULT to an
   existing table? That fails on tables with rows, or locks them.
3. Indexes: does every new foreign key column have an index?
4. Data: does it delete or rewrite existing rows?

Format each line as:

    <n>. <name>: PASS|FAIL - <reason>

End with exactly one of these lines:

    Verdict: APPROVE
    Verdict: REQUEST CHANGES

Request changes if any check fails. Do not edit the migration yourself;
the author fixes it.

What the model sees up front

run_task() builds the system prompt with catalog_prompt() from skills.py. For these two skills, this is the whole skills section the model sees on every call:

Skills available (load one with the use_skill tool when relevant):
- release-note: How to write a release note for a change in this project
- review-migration: How to review a database migration before it is merged

That is 214 characters, against 1,517 characters for the two full skills. The model pays for a skill's full text only in the conversations that need it. With twenty skills, the catalog grows by one line each; the full texts would not fit in every prompt.

How a skill is loaded

use_skill is an ordinary tool, from skill_tools() in skills.py. The model passes a skill name; the tool looks it up in the catalog and returns the file's text as the tool result. It never takes a path, so it cannot be used to read other files. It only reads, so the gate treats it as a read tool and allows it in every mode.

sequenceDiagram
    participant M as model
    participant RL as run_loop()
    participant S as use_skill
    participant F as skills/release-note/SKILL.md

    Note over M: system prompt lists:
release-note, review-migration
    M->>RL: use_skill(name="release-note")
    RL->>S: run(name="release-note")
    S->>F: look up in catalog, read file
    F-->>S: the instructions
    S-->>RL: tool result = full SKILL.md text
    RL-->>M: instructions now in the conversation
    M->>RL: write_file(RELEASE_NOTES.md, entry in that format)

The project

The script builds a throwaway project in a temporary folder and copies the skills into its skills/ folder, where skills.py looks for them:

<tmp>/calc.py                            the fixed average()
<tmp>/RELEASE_NOTES.md                    just the heading "# Release notes"
<tmp>/migrations/0002_add_email.up.sql    the migration to review
<tmp>/skills/release-note/SKILL.md
<tmp>/skills/review-migration/SKILL.md

RELEASE_NOTES.md has no earlier entries on purpose: with one to copy, the model could match the format without reading the skill. The migration has three problems the checklist should catch:

# migrations/0002_add_email.up.sql
-- 0002: give users an email address and link orders to users
ALTER TABLE users ADD COLUMN email TEXT NOT NULL;
ALTER TABLE orders ADD COLUMN user_id INTEGER REFERENCES users(id);

No .down.sql exists (not reversible), email is NOT NULL with no default (locking), and user_id is a foreign key with no index. It deletes no data. The expected verdict is REQUEST CHANGES.

The three tasks

Each task is a fresh conversation through run_task() in safe mode. The approver allows file writes (write_file, edit_file) and refuses everything else, including bash, which no task needs.

#Task (as sent)Skill it should loadCheck
1“We fixed a bug in calc.py … Add a release note for version 1.0.1, dated <today>.” release-note only The new entry in RELEASE_NOTES.md matches the skill's format: heading, ### Fixed, the file in brackets, an Upgrade: line.
2“In one sentence: what does average() in calc.py return?” none No use_skill call at all.
3“Review the migration migrations/0002_add_email.up.sql.” review-migration only The answer has four numbered PASS|FAIL - reason lines and a Verdict: line.

The task wording never mentions a skill or a format. Choosing the skill is the model's job, from the one-line descriptions alone.

How to run

0. Install the package (once)

From the odysseus project folder.

pip install -e .

1. Offline: no provider, no key

A scripted “model” replays the calls a real one should make. The skills, the catalog, use_skill, the gate and the format checks are all real.

python3 demos/skills/skills.py --offline

2. Live: a real model

Set the provider and key exactly as for the dice demo, then:

python3 demos/skills/skills.py

Add --keep to keep the temporary project, for example to read the RELEASE_NOTES.md the model wrote.

Analysis

Offline: every check passes. This proves the plumbing, not the model: the catalog reaches the system prompt, use_skill returns the right file by name, the gate allows it, and the format checks recognise a correct entry and review.

  • Context: the catalog costs 214 characters per call; the two full skills are 1,517. Each task loaded at most one skill, so no task paid for the other.
  • Task 2 loaded nothing. A question about the code needs no instructions, and the conversation never contains either skill's text.
  • Task 3 loaded the skill and read the file in the same reply. The loop runs calls in order, so the checklist was in the conversation before the model wrote its review.

Live run: every check passes

The model chose the right skill every time, from the one-line descriptions alone. The tasks never mention skills.

TaskSkills loadedFollowed the skill?
1. release noterelease-note Yes. Heading, ### Fixed, the file in brackets and the Upgrade: line, exactly as the skill says.
2. questionnone Nothing to follow: it answered from calc.py, and neither skill's text entered the conversation.
3. migration reviewreview-migration Yes. All four checks in order, the right three failures with correct reasons, and Verdict: REQUEST CHANGES.
  • It loaded the skill first. In tasks 1 and 3, use_skill was the model's first call, before it had read any project file. The description was enough to decide.
  • It obeyed the skill's rules, not just its format. Task 1 read RELEASE_NOTES.md before writing, as “never edit or reorder older entries” requires. Task 3 checked for a .down.sql with list_files rather than assuming, and did not edit the migration: “the author fixes it”.
  • It said what it had assumed. The skill requires an Upgrade: line; the model chose “no action needed”, gave its reason (a calculation fix needs nothing from users) and added: “I didn't open calc.py, so the note rests on your description of the bug.” A skill can make a model fill in a field; it cannot make the content right, so this kind of note is worth having.
  • Context cost. Task 2's first request was 1,648 input tokens; task 1's first request, before loading the skill, was 1,696. The difference is the task text. The skills cost nothing extra until loaded, then a few hundred tokens for the one task that needed them.

Something to watch

Skills are trusted instructions. A skill's text enters the conversation as a tool result, and the model is told to follow it. Anyone who can add a folder under skills/ can steer the agent: a skill could tell it to run commands or send files somewhere. Review skills the way you review code.

The description is the whole selection mechanism. The model chooses from one line per skill. A vague description (“database stuff”) gets a skill loaded for the wrong tasks or not at all. Write it as “how to <task>”, the way both skills here do.
